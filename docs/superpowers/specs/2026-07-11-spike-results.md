# Spike-Ergebnisse Modernisierung (Etappe 2)

## Spike A: RDF4J-3.6-Client ↔ RDF4J-5-Server
- Server-Image/Tag: `eclipse/rdf4j-workbench:5.1.2` (Tag existiert auf Docker Hub, kein Fallback noetig)
- Protokollversion Server: `12` (verifiziert via `curl http://localhost:8090/rdf4j-server/protocol`)
- **Pfad-Inkompatibilitaet:** Der Kontextpfad des offiziellen Images ist `/rdf4j-server` (Tomcat-Webapp `rdf4j-server.war`), NICHT `/rdf4j` wie im Brief angenommen bzw. wie es der service-eigene, aus dem Quellcode gebaute `triplestore-*-war-exec.jar` verwendet. `curl http://localhost:8090/rdf4j/protocol` liefert `404`; kein Docker-Run-Env am offiziellen Image erlaubt eine Aenderung des Kontextpfads (verifiziert per `docker inspect` und `docker exec ... ls /usr/local/tomcat/webapps/`: nur `rdf4j-server.war`/`rdf4j-workbench.war` vorhanden, kein `rdf4j.war`). Fuer den eigentlichen Client-Test ist das folgenlos, weil der `ajan.e2e.triplestoreUrl`-Hook die volle Basis-URL parametrisiert (`http://localhost:8090/rdf4j-server` statt `.../rdf4j`) — der RDF4J-Client bindet sich an eine konfigurierbare Basis-URL, der Pfadname selbst ist kein Protokollbestandteil.
- **Abweichung vom Brief (E2E-Harness):** In `e2e/pom.xml` wurde die Weiterleitung des `-Dajan.e2e.triplestoreUrl=...`-Systemproperty an die geforkte Failsafe-Test-JVM **explizit deklariert**: Default-leere Property `<ajan.e2e.triplestoreUrl></ajan.e2e.triplestoreUrl>` ergaenzt und in `<systemPropertyVariables>` als `<ajan.e2e.triplestoreUrl>${ajan.e2e.triplestoreUrl}</ajan.e2e.triplestoreUrl>` durchgereicht. Zweck: Der Hook-Vertrag steht sichtbar im POM und haengt nicht von der Surefire-/Failsafe-internen Property-Propagation ab. Kein Produktcode betroffen, nur das E2E-Testharness.
  - **Korrektur (Whole-Branch-Review Etappe 2):** Die urspruengliche Begruendung dieser Aenderung war eine Fehldiagnose und ist hiermit **widerlegt** — sie stand hier zuvor als „Failsafe leitet System-Properties bei `forkCount=1` nicht automatisch weiter, ohne den Fix war der Spike gar nicht durchfuehrbar". Belege des Reviews: (1) Mit dem byte-identischen Pre-Fix-POM (`git show acb072e5:e2e/pom.xml`) unter Maven 3.9.16, failsafe 3.2.5, JDK 11, `forkCount=1`/`reuseForks=true` kommt `-Dajan.e2e.triplestoreUrl=...` sehr wohl in der geforkten Test-JVM an (per `System.getProperty` in einem Probe-IT ausgelesen, aus dem Modulverzeichnis und per `-f` von der Repo-Wurzel). (2) `org.apache.maven.plugin.surefire.SurefireProperties.calculateEffectiveProperties` (per `javap` geprueft) kopiert Maven-User-Properties (`-D`) als letzte Quelle in die Fork-Properties; sie ueberschreiben `systemPropertyVariables` sogar. Die im Original-Report behauptete Port-8090-Kollision stand dort durchgehend im Konjunktiv und wurde nie beobachtet. **Daraus folgt keine allgemeine Regel** wie „jede Property muss in `systemPropertyVariables` deklariert werden, sonst greift sie nicht" — Planautoren der Etappen 3–6 duerfen eine solche Regel nicht uebernehmen. Die Konfiguration selbst bleibt bestehen (harmlos, explizit, robust gegen kuenftige Surefire-Versionen).
- Kommando: `mvn -f e2e/pom.xml verify -Dajan.e2e.triplestoreUrl=http://localhost:8090/rdf4j-server` (JDK 11)
- **E2E-Ergebnis: rot** — 16 Tests, 10 Failures, 0 Errors, 0 Skipped:
  - `AgentLifecycleIT`: 6/6 Failures
  - `RdfResponseIT`: 4/4 Failures
  - `ErrorPathIT`: 3/3 gruen
  - `PluginLoadIT`: 1/1 gruen
  - `SystemSmokeIT`: 2/2 gruen
  - Root-Cause-Kette: Der erste Fehler ist ein 500 bei `createAgentFromHelloWorldTemplate`:
    ```
    org.opentest4j.AssertionFailedError: agent creation should succeed, was 500:
    <Map xmlns=""><timestamp>1785491504952</timestamp><status>500</status>
    <error>Internal Server Error</error>
    <exception>org.jboss.resteasy.spi.UnhandledException</exception>
    <message>de.dfki.asr.ajan.common.exceptions.TripleStoreException: Unable to query repository!</message>
    <path>/ajan/agents/</path></Map> ==> expected: <200> but was: <500>
    ```
    Ursprung im Produktcode: `common/src/main/java/de/dfki/asr/ajan/common/SPARQLUtil.java`, Methode `queryRepository(Repository, String)` — wraps `Repositories.graphQuery(repo, query, ...)` (RDF4J-3.6-Client-API) und wirft bei jeder Exception `TripleStoreException("Unable to query repository!", ex)`. Die urspruengliche Root-Cause-Exception (vermutlich ein Protokoll-/Antwortformat-Unterschied des RDF4J-5-Servers gegenueber dem, was der 3.6-Client bei einer GraphQuery erwartet) wird von RESTEasy nicht als Stacktrace geloggt — `e2e/target/logs/service.log` enthaelt nach dem Undertow-Start (`Started Application in 7.344 seconds`) keine weiteren ERROR-/Exception-Zeilen; die einzige verfuegbare Diagnose ist die o.g. HTTP-Response. Root-Causing der exakten Wire-Format-Differenz haette einen Debugger oder eine Logging-Config-Aenderung im Produktcode erfordert, was ausserhalb des Scopes von Spike A liegt (reine Beobachtung).
  - Beobachtung, die die Root-Cause stuetzt: Die einfache Repository-Auflistung (`GET .../repositories`) funktioniert einwandfrei — der Fehlschlag von `agentKnowledgeVisibleInTriplestore` zeigt alle 6 erwarteten Repositories (`editor_data`, `domain`, `behaviors`, `services`, `node_definitions`, `agents`) korrekt unter `http://localhost:8090/rdf4j-server/repositories/...`. Der Bruch tritt erst bei der tatsaechlichen SPARQL-GraphQuery (Anlegen/Abfragen von Agenten-Daten) auf, nicht bei der reinen Protokoll-Handshake- oder Verwaltungsebene.
  - Alle nachfolgenden Failures in `AgentLifecycleIT`/`RdfResponseIT` sind Folgefehler derselben Ursache (Agent wurde nie erfolgreich angelegt → `AgentNotFoundException` bei GET/DELETE/Message-Endpunkten, 404 statt 200).
  - `ErrorPathIT`, `PluginLoadIT`, `SystemSmokeIT` bleiben gruen, weil sie keine neuen Agenten ueber eine GraphQuery gegen den Triplestore anlegen, sondern nur bereits ueber die TTL-Initialdaten geladene bzw. rein serverseitige Zustaende pruefen.
- **Entscheidung:** Triplestore-Neubau als eigenstaendige Etappe 3: **ja**. Der bestehende RDF4J-3.6-Client des Service-Produktcodes (`common/.../SPARQLUtil.java`, `Repositories.graphQuery`) ist gegen einen RDF4J-5-Server nachweislich NICHT funktionsfaehig fuer den zentralen Anwendungsfall (Agent-Anlegen/-Abfragen per SPARQL-GraphQuery) — 10 von 16 E2E-Tests schlagen fehl, alle mit derselben Fehlerkette. Ein direkter Sprung auf einen RDF4J-5-Server ohne vorherige Client-Migration wuerde den Produktivbetrieb brechen. Der Triplestore-Client-Umstieg (RDF4J 3.6 → 5.x im Produktcode, inkl. API-Anpassung an `Repositories`/`RepositoryConnection`-Aenderungen) muss daher als eigene, isolierte Etappe vor dem groesseren Boot/Java-Kern-Sprung geplant werden, mit eigener Testabdeckung fuer genau die hier gefundene GraphQuery-Bruchstelle.

## Spike B: RESTEasy-Spring-Boot-Starter unter Boot 4
- Boot-Version: 4.1.0, Starter-Version: resteasy-servlet-spring-boot-starter 6.3.0.Final (groupId `org.jboss.resteasy` — die Brief-Vorlage hatte die falsche GroupId `org.jboss.resteasy.spring.boot`, die auf Maven Central nicht existiert)
- Ergebnis: gruen. `GET http://localhost:18080/api/hello` -> HTTP 200, body `hello`, ausgeliefert ueber `JaxrsConfig`/`HelloResource` (echte JAX-RS-Annotationen) via RESTEasy auf Boot 4.1.0 + JDK 21. Voraussetzung: `spring-boot-starter-web` muss zusaetzlich zum RESTEasy-Starter ergaenzt werden (der Starter selbst deklariert keine einzige transitive Abhaengigkeit — das ist kein Boot-4-Spezifikum, sondern gilt genauso unter Boot 3.x). Eine harmlose Start-WARN bleibt bestehen (`TypeNotPresentException: Type ...WebMvcAutoConfiguration not present` bei der Introspektion von `ResteasyAutoConfiguration`); beeintraechtigt weder Start noch Endpoint.
- **Geltungsbereich:** „gruen" ist nur fuer den getesteten Minimalpfad belegt — ein einzelner `@Path`/`@GET`-Endpunkt ohne Provider, ohne ExceptionMapper, ohne Filter/Interceptor, ohne Content-Negotiation. Die WARN `TypeNotPresentException: ...WebMvcAutoConfiguration not present` ist dabei kein rein kosmetisches Detail, sondern ein Hinweis darauf, dass `ResteasyAutoConfiguration` unter Boot 4 nur teilweise auswertbar ist und der Starter laut Release Notes offiziell gegen Boot 3.4 gebaut ist. Fuer den vollen REST-Layer (Provider/Filter/Interceptor/Content-Negotiation) ist damit noch nichts verifiziert.
- **Offener Rest fuer Etappe 4 (Scope-Luecke zum Produktcode):** Der Spike validiert nur den Nachfolge-Starter selbst, nicht die Migration der bestehenden RESTEasy-3-APIs im Produktcode. `executionservice/pom.xml:136-141` zieht `com.paypal.springboot:resteasy-spring-boot-starter:2.0.0-RELEASE` (runtime scope), `executionservice/pom.xml:157-166` zusaetzlich `org.jboss.resteasy:resteasy-spring:3.0.9.Final`. `executionservice/src/main/java/de/dfki/asr/ajan/executionservice/ResteasyServletContext.java:27-28,36,46` importiert und nutzt `org.jboss.resteasy.spi.ResteasyProviderFactory` sowie die Annotation `@org.jboss.resteasy.annotations.interception.ServerInterceptor` (zusammen mit `javax.ws.rs.*`, nicht `jakarta.ws.rs.*`). Verifiziert: Das Package `org.jboss.resteasy.annotations.interception` (inkl. `ServerInterceptor`) existiert nur in den alten RESTEasy-3.0.x-Jars (`resteasy-jaxrs:3.0.9.Final`/`3.0.16.Final`, lokal im `.m2`-Cache geprueft) und ist in keinem der lokal verfuegbaren RESTEasy-6.x-Jars (`resteasy-core`/`resteasy-core-spi:6.2.11.Final`) mehr enthalten — die Annotation ist in RESTEasy 6 entfernt. `ResteasyProviderFactory` existiert als Klasse zwar noch in `resteasy-core-spi:6.2.11.Final`, aber der komplette Code ist zusaetzlich auf dem alten `javax.*`-Namespace aufgebaut, den RESTEasy 6/Jakarta EE 9+ nicht mehr bedient. „JAX-RS-Port" im Kern-Sprung ist also nicht nur ein Dependency-Tausch, sondern erfordert eine echte Migration von `ResteasyServletContext.java` (und moeglicher weiterer Stellen mit `ResteasyProviderFactory`/`@ServerInterceptor`/`javax.ws.rs.*`) auf die RESTEasy-6/Jakarta-APIs.
- **Entscheidung:** REST-Layer im Kern-Sprung: JAX-RS-Port

## Konsequenzen fuer die Folgeplaene

Konsolidiert am 2026-07-31 (Task 13, Entscheidungs-Gate Ende Etappe 2). Diese vier Zeilen sind die Entscheidungsgrundlage fuer Plan 2 (Etappe 3) und Plan 3 (Etappen 4–6); die dazugehoerigen Spec-Korrekturen stehen in `2026-07-11-java-modernization-design.md`.

- **Etappe 3 (Triplestore) eigenstaendig: ja** (Spike A) — **aber mit erweitertem Umfang**, und unter bewusster Ueberschreibung einer vorregistrierten Regel.

  *Befund:* Spike A hat widerlegt, dass der alte Service unveraendert gegen einen RDF4J-5-Server laufen kann (10/16 E2E rot, alle auf `Repositories.graphQuery` in `common/src/main/java/de/dfki/asr/ajan/common/SPARQLUtil.java` zurueckfuehrbar). Damit ist zweierlei ausgeschlossen: Etappe 3 als blosser Server-WAR-Tausch (sie endete mit roter E2E-Suite und verletzte die Etappen-Invariante aus Spec Abschnitt 4), und das bisherige Spec-Abnahmekriterium „alter Service gegen neuen Triplestore".

  *Vorregistrierte Regel und Override:* Spec Abschnitt 4 und Risiko 3 hatten vorab festgelegt: „falls inkompatibel, wandert der Triplestore-Neubau in den Kern-Sprung (Etappe 4)". Genau diese Regel wird hier **bewusst ueberschrieben** — Etappe 3 bleibt eigenstaendig und wird stattdessen um den Client-Umstieg erweitert. **Der Auftraggeber hat diesen Override am 2026-07-31 ausdruecklich bestaetigt** (Option „Etappe 3 erweitern"), inkl. der Feststellung, dass die vorregistrierte Regel damit ausser Kraft gesetzt ist.

  *Begruendung des Overrides* (nicht die Etappen-Invariante — die schliesst nur den blossen Server-Tausch aus und traegt die Wahl zwischen den beiden Alternativen nicht): Der RDF4J-Bruch soll vom Boot-4-/Java-21-Sprung **isoliert** bleiben. Wuerde alles in Etappe 4 zusammenfallen, kaemen bei einer roten E2E-Suite gleichzeitig RDF4J-Major, Boot-Major, Jakarta-Namespace, Java-21-Bump und Container-Wechsel als Ursache in Frage; als eigene Etappe ist eine rote E2E-Suite eindeutig dem RDF4J-Umstieg zuzuordnen und einzeln revertierbar. Das ist auch die Linie der Spike-A-Entscheidung selbst („muss daher als eigene, isolierte Etappe vor dem groesseren Boot/Java-Kern-Sprung geplant werden").

  *Umfang von Etappe 3:* (1) neues Embedded-Tomcat-Launcher-Modul mit RDF4J-5-WARs (identische Ports/Pfade/CLI); (2) RDF4J-Client-Umstieg 3.6.3 → 5.x im Produktcode inkl. der API-Anpassungen an `Repositories`/`RepositoryConnection`; (3) gezielte Testabdeckung fuer genau die gefundene GraphQuery-Bruchstelle; (4) bewusste Entscheidung ueber den RDF4J-Pin der E2E-Suite (`e2e/pom.xml:30-45`, `rdf4j-rio-turtle`/`rdf4j-model` 3.6.3, test-scope): mitziehen auf 5.x oder bewusst alt lassen — der Kommentar „Same RDF4J line as the current project" stimmt nach Etappe 3 nicht mehr und ist in jedem Fall zu korrigieren; die Suite testet nur von aussen und soll alle Etappen unveraendert ueberleben.

  *Reichweite von (2) — am Repo verifiziert, deutlich groesser als nur die Kernmodule:* Die RDF4J-Version ist **zentral** im Parent-POM verwaltet (`pom.xml`, `<org.eclipse.rdf4j.version>3.6.3</org.eclipse.rdf4j.version>`). Ein Bump auf 5.x zieht daher zwingend mit:
  - `rdfbeans` (gevendort), `common`, `behaviour`, `functions`;
  - **das gesamte Pluginsystem**: 9 POMs deklarieren `rdf4j-model`/`rdf4j-repository-api` (`pluginsystem/pom.xml` plus die 8 Plugin-POMs ASP, Mapping, MOSIM, MQTT, Python, RMLMapping, STRIPS, StandardBTNodes), und **75 Java-Dateien in allen 10 Plugins** importieren `org.eclipse.rdf4j.*` (OPCUAPlugin 4 und ScriptExecutorPlugin 1 erben die Dependency aus `pluginsystem/pom.xml`, ohne sie selbst zu deklarieren). Verteilung: MOSIM 21, StandardBTNodes 14, Mapping 11, MQTT 10, ASP 6, STRIPS 6, OPCUA 4, Python 1, RMLMapping 1, ScriptExecutor 1.

  Etappe 3 muss also Plugin-Compile **und** `PluginLoadIT` mit abdecken; sie ist keine Zwei-Modul-Etappe. Nicht enthalten bleibt alles Nicht-RDF4J am Pluginsystem (pf4j-Bump, Jakarta, Java 21) — das bleibt Etappe 4.

  *Java-Version:* Die Java-Version steht Etappe 3 auf Java 11 **nicht entgegen** — RDF4J 5.x verlangt laut https://rdf4j.org/download/ minimal Java 11 („RDF4J 5.3.1 … requires Java 11 minimally"). Das ist die notwendige, **nicht** die hinreichende Bedingung: ob RDF4J 5.x transitiv im Boot-1.3-Kontext traegt, ist offene Frage 4 — dort steht auch die vom Auftraggeber mitbeschlossene Rueckfallebene.

  *Kontextpfad:* Das neue Launcher-Modul behaelt normativ `/rdf4j` (Kompatibilitaet mit bestehenden Konfigurationen und Start-Skripten), auch wenn das offizielle `eclipse/rdf4j-workbench`-Image `/rdf4j-server` verwendet. Der Client bindet an eine konfigurierbare Basis-URL, der Pfadname ist kein Protokollbestandteil — der Unterschied betrifft nur das Docker-Image, nicht den geplanten Launcher. Das ist entschieden, keine offene Frage.
- **REST-Layer Kern-Sprung: JAX-RS-Port** (Spike B) — Richtung bestaetigt, Aufwand aber deutlich groesser als „nur javax→jakarta-Imports". Konkrete Koordinaten: `org.jboss.resteasy:resteasy-servlet-spring-boot-starter:6.3.0.Final` **plus** `spring-boot-starter-web` (der Starter bringt keine transitiven Abhaengigkeiten mit). Umfang fuer Etappe 4: (1) `com.paypal.springboot:resteasy-spring-boot-starter:2.0.0-RELEASE` (`executionservice/pom.xml:136-141`) und `org.jboss.resteasy:resteasy-spring:3.0.9.Final` (`executionservice/pom.xml:157-166`) entfernen und durch den offiziellen Starter ersetzen; (2) `executionservice/src/main/java/de/dfki/asr/ajan/executionservice/ResteasyServletContext.java` umbauen — `@org.jboss.resteasy.annotations.interception.ServerInterceptor` ist in den geprueften RESTEasy-6-Jars (`resteasy-core`/`resteasy-core-spi:6.2.11.Final`, lokal im `.m2`-Cache verifiziert) nicht mehr enthalten; die entschiedene Starter-Version zieht `6.3.0.Final`, dort wurde es nicht gegengeprueft — dass die Annotation dort wieder existiert, ist unwahrscheinlich, aber unbelegt. Die Filter-/Interceptor-Registrierung ist damit auf die JAX-RS-2.1-Mechanik umzustellen; welche konkret, ist offene Frage 2. `ResteasyProviderFactory` existiert nur noch unter `jakarta.*`; (3) `javax.ws.rs.*` → `jakarta.ws.rs.*` ueber alle ~26 REST-Klassen (~100 `javax.*`-Imports). **Restrisiko:** Spike B belegt nur den Minimalpfad (ein `@Path`-GET, keine Provider, ExceptionMapper, Filter/Interceptor, Content-Negotiation); der Starter ist offiziell gegen Boot 3.4 gebaut und `ResteasyAutoConfiguration` ist unter Boot 4 nur teilweise auswertbar (WARN `TypeNotPresentException: ...WebMvcAutoConfiguration not present`). Der MVC-Umbau bleibt als Plan B stehen, falls der volle REST-Layer scheitert; er ist aber nicht mehr der geplante Weg.
- **Servlet-Container: Tomcat** (Spike C) — Undertow ist unter Boot 4.1.0 keine Option (`spring-boot-starter-undertow` wird von `spring-boot-dependencies:4.1.0` nicht mehr verwaltet; das verwaiste `4.0.0-M1` ist binaer inkompatibel). Fuer Etappe 4 heisst das: `spring-boot-starter-tomcat` statt Undertow, und die heutigen Undertow-spezifischen Defaults/Properties des Boot-1.3-Setups muessen beim Umstieg gegengeprueft werden (siehe Spec-Risiko 6).
- **pf4j-Zielversion + Loader-Aufwand: 3.15.0, Loader-Aufwand fuer den getesteten Pfad minimal** (Spike D) — unter JDK 21 gruen gegen das reale Fat-JAR-Deployment (`StandardBTNodes-0.1-all.jar`, `state=RESOLVED`); das Fat-JAR-/Deployment-Mode-Resolutionsverhalten bleibt fuer `loadPlugins()` unveraendert, das Plugin-Deployment-Format muss nicht angefasst werden. Bekannte Anpassung in `pluginsystem/loader/src/main/java/de/dfki/asr/ajan/pluginsystem/AJANPluginLoader.java`: `LegacyExtensionFinder` → `IndexedExtensionFinder` (kein Muss zum Kompilieren, aber die deprecated Klasse sollte nicht neu zementiert werden). **Geltungsbereich (analog Spike B):** Der Spike benutzte den Stock-`DefaultPluginManager` und nur `loadPlugins()`/`getPluginState()`; Plugin-Start, Extension-Aufloesung ueber den ueberschriebenen `createExtensionFinder()` und `provided`-Scope-Handling sind unbelegt (offene Frage 6). Plan 3 darf den pf4j-Schritt daher nicht als reinen Versions-Bump budgetieren.

### Offene Fragen (kein Spike deckt sie ab)

1. **Voller REST-Layer unter Boot 4** — ob Provider, ExceptionMapper, Filter/Interceptor und Content-Negotiation des AJAN-REST-Layers unter `resteasy-servlet-spring-boot-starter:6.3.0.Final` + Boot 4.1.0 tragen, ist offen. Erst der Umbau in Etappe 4 beantwortet das; die Plan-3-Erstellung sollte einen expliziten Abbruch-/Umschaltpunkt auf den MVC-Plan-B vorsehen.
2. **Ersatzmechanik fuer `@ServerInterceptor`** — welche konkrete JAX-RS-2.1-Registrierung (`@Provider` + `ContainerRequestFilter`/`ContainerResponseFilter`, `DynamicFeature`, o.ae.) das bisherige Verhalten von `ResteasyServletContext` 1:1 abbildet, ist nicht spiketechnisch belegt und muss beim Umbau entschieden werden.
3. **Exakte Wire-Format-Differenz in Spike A** — die eigentliche Root-Cause-Exception hinter `TripleStoreException: Unable to query repository!` wurde bewusst nicht bis auf die Protokollebene aufgeloest (haette Debugger oder Logging-Aenderung im Produktcode erfordert). Fuer Plan 2 ist das folgenlos (der Client wird ohnehin auf 5.x gehoben), fuer die Testabdeckung in Etappe 3 ist es aber der Ausgangspunkt.
4. **RDF4J 5.x im Boot-1.3-/Java-11-Kontext (Etappe 3)** — kein Spike hat den RDF4J-5-Client *im bestehenden executionservice* laufen lassen; Spike A hat nur den alten Client gegen den neuen Server getestet. Dass RDF4J 5.x minimal Java 11 verlangt, ist die notwendige, nicht die hinreichende Bedingung. Ob RDF4J 5.x transitiv mit dem Boot-1.3-Dependency-Management vertraeglich ist (Jackson, httpclient, slf4j) und ob Etappe 3 deshalb einzelne Versions-Pins braucht, muss Plan 2 als erste Risikofrage klaeren. **Rueckfallebene (vom Auftraggeber am 2026-07-31 mitbeschlossen):** Traegt RDF4J 5.x unter Boot 1.3 / Java 11 transitiv nicht, wird Etappe 3 doch mit Etappe 4 zusammengelegt. **Beantwortet durch Gate E (Plan 2, Task 1, s.o.):** ja, RDF4J 5.3.1 traegt unter Boot 1.3.5 / Java 11 ohne jeden Versions-Override — Rueckfallebene nicht gezogen.
5. **Tomcat-Version des neuen Launcher-Moduls** — die Spec sieht Embedded Tomcat auf der Jakarta-Linie vor; Tomcat 11 verlangt Java 17, Etappe 3 laeuft aber noch auf Java 11. Plan 2 muss die konkrete Embedded-Tomcat-Version festlegen (und ggf. in Etappe 4 mit dem Java-21-Bump nachziehen). Kein Spike deckt das ab.
6. **pf4j-Verhalten jenseits von `loadPlugins()`, inkl. `provided`-Handling (Etappe 4)** — Spike D belegt nur die Fat-JAR-Resolution mit dem Stock-`DefaultPluginManager` (`spikes/pf4j-java21/src/main/java/spike/PluginLoadCheck.java` ruft `loadPlugins()` und liest `getPluginState()`, mehr nicht). Unbelegt bleiben unter pf4j 3.15.0: (a) `startPlugins()`, (b) die Extension-Aufloesung (`getExtensions(...)`) ueber den in `pluginsystem/loader/src/main/java/de/dfki/asr/ajan/pluginsystem/AJANPluginLoader.java` **ueberschriebenen** `createExtensionFinder()` mit `LegacyExtensionFinder`/`IndexedExtensionFinder`, (c) das **`provided`-Scope-Handling** der Plugin-Builds (im urspruenglichen Spec-Risiko 4 ausdruecklich als Risikoquelle genannt, vom Spike nicht adressiert). Plan 3 muss dafuer Budget und einen Ladecheck ueber den echten `AJANPluginLoader` (`PluginLoadIT`, Entwicklungs- **und** Deployment-Modus) vorsehen.
